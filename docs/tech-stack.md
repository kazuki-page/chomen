# 技術選定の理由と役割

このアプリが何でできていて、なぜそれを選んだかをまとめた文書。
表面的な「流行っているから」ではなく、**この案件の条件から何が導かれたか**を書く。

前提となる条件は3つ。

1. **利用者は家族のみ**（自分と両親）。同時アクセスはごく少数で、データ量も小さい
2. **月額費用をかけたくない**。家族のための道具に固定費を発生させたくない
3. **保守するのは自分1人**。数か月触らない期間があっても読み解ける状態を保つ必要がある

この3つが、以下のほぼすべての判断の理由になっている。

---

## 1. 全体像 — リクエストが通る道

技術の名前を覚えるより、**1回の画面表示で何がどう動くか**を掴むほうが早い。
ブラウザで `/units`（部屋一覧）を開いたときの流れ。

```
[ブラウザ]  /units（部屋一覧）を開く
     │
     ▼
[Cloudflare のエッジ]  世界中の拠点のうち、一番近いところで Worker が起動
     │                 → workers/app.ts の fetch ハンドラ
     │                 → HTTP なら HTTPS へリダイレクト
     │
     ▼
[React Router]  app/routes.ts を見て「/units は app/routes/units.tsx」と解決
     │
     ▼
[loader]  units.tsx の loader がサーバー上で動く
     │      ├─ requireOrg() … Better Auth でログイン確認 → 所属組織を確定
     │      └─ listUnits(ctx) … リポジトリ関数を呼ぶ
     │            │
     │            ▼
     │      [Drizzle]  TypeScript の記述から SQL 文を組み立てる
     │            │
     │            ▼
     │      [D1]  SQLite が結果を返す
     │
     ▼
[React]  受け取ったデータで HTML を組み立てる（サーバー側でレンダリング）
     │
     ▼
[ブラウザ]  HTML が届いて即表示 → その後 React が引き継いで操作可能になる
```

書き込み（フォーム送信）も同じ道を通る。違うのは `loader` ではなく **`action`** が動く点だけ。
`action` が終わると React Router が自動で `loader` を再実行するので、
「保存したのに画面が古いまま」が構造的に起きない。

**この「1本道」が、この構成を選んだ一番の理由。**
フロントとサーバーを別々のプロジェクトとして作り、その間を API で繋ぐ構成に比べて、
覚えることも壊れる箇所も少ない。1人で保守する前提では、これが効く。

---

## 2. Cloudflare Workers — アプリが動く場所

### 役割

サーバー。ただし「借りたマシンが常時起動している」のではなく、
**リクエストが来た瞬間だけ、世界中のエッジ拠点で起動して消える。**

### なぜ選んだか

- **無料枠で足りる。** 1日10万リクエストまで無料。家族だけの利用では到底使い切らない
- **サーバーの管理が要らない。** OSの更新もSSHも要らない。保守が自分1人なので、
  管理対象は少ないほどいい
- **落ちている時間が実質ない。** 個人のVPSと違い、拠点が1つ死んでも他が受ける

条件2（費用）と条件3（1人保守）から、ほぼ自動的にこうなった。

### 代わりにあった選択肢

| 選択肢 | 見送った理由 |
|---|---|
| VPS（さくら・ConoHa等） | 月額が発生し、OS更新やバックアップの管理も自分の仕事になる |
| Vercel | 使いやすいが Next.js 前提の面が強く、無料枠の商用利用条件も気になる |
| Firebase | 認証とDBは楽だが、データが増えると課金が読みにくい |

### 弱点（ここは理解しておくべき）

Workers は **Node.js ではない。** V8 という JavaScript エンジンだけが動く環境で、
Node.js の機能は一部しか使えない（`nodejs_compat` フラグで足りない分を補っている）。

この制約が実際に効いた場面が1つある。**メール送信ができない。**
Workers は生のTCP接続を張れないため、SMTP が使えない。
これが後述の Resend を入れた理由。

## 3. React Router v8（framework mode）— アプリの骨格

### 役割

3つを1つでやる。

1. **ルーティング** … どのURLでどの画面を出すか
2. **データの受け渡し** … `loader`（読み込み）と `action`（書き込み）
3. **サーバーレンダリング（SSR）** … HTMLをサーバー側で組み立ててから返す

### なぜ選んだか

**Cloudflare Workers の上でそのまま動くから。**

一番の対抗馬は Next.js だった。日本の求人でも圧倒的に多い。
ただし Next.js を Cloudflare で動かすには **OpenNext** という変換層を挟む必要がある。
Next.js の新バージョンが出るたびに OpenNext の対応を待つことになり、
**自分1人で保守するアプリに、自分でコントロールできない依存を挟みたくなかった。**

React Router は Workers を正式にサポートしていて、間に何も挟まらない。

### framework mode とは

React Router には2つの使い方がある。

- **library mode** … 画面の切り替えだけを担当する。データ取得は自分で書く（従来の使い方）
- **framework mode** … ルーティング＋データ取得＋SSR まで面倒を見る（今回はこちら）

framework mode は、もともと **Remix** という別のフレームワークだった。
それが React Router に統合されて v7 以降 framework mode になった。
なので「Remix の経験」として語れる部分がかなり重なる。

### `loader` と `action` の考え方

ここが一番の特徴なので、理解しておく価値がある。

```
画面を開く    → loader が動く（サーバー）→ データを返す
フォーム送信  → action が動く（サーバー）→ 保存 → loader が自動で再実行
```

**素のHTMLのフォーム送信に近い。** `fetch()` を書いて、ローディング状態を管理して、
成功したら一覧を再取得して……という手作業が要らない。

副次的な効果として、**JavaScript が動かない状況でもフォームが機能する。**
両親が使う端末で何かがうまく読み込まれなくても、最低限の操作は通る。

## 4. TypeScript — 型のある JavaScript

### 役割

変数や関数に「これは文字列」「これは部屋の情報」といった型を付ける。
食い違いがあれば、実行する前にエディタとビルドが教えてくれる。

### なぜ選んだか

**扱っている概念が多く、しかも似ているから。**

このアプリには「部屋（unit）」「契約（lease）」「入居者（tenant）」「家賃改定（rent_revision）」
「手続き（procedure）」がある。どれもIDが文字列で、取り違えても見た目では気づけない。
`leaseId` を渡すべきところに `unitId` を渡す、といった間違いを型が止める。

もう1つは条件3。**数か月後の自分は他人。**
型は「この関数が何を受け取って何を返すか」の説明書として常に最新に保たれる。

## 5. Cloudflare D1 — データベース

### 役割

データの保管場所。**実体は SQLite**（1ファイルで完結する軽量なSQLデータベース）を
Cloudflare が分散配置できるようにしたもの。SQL はそのまま使える。

### なぜ選んだか

- **Workers から設定なしで繋がる。** 接続文字列もコネクションプールも要らない
- **無料枠で足りる。** このアプリのデータは、写真を除けば数MBにもならない
- **SQLite で十分すぎる。** 同時アクセスが数人であれば、性能の心配をする必要がない

### 弱点（3つとも実装に影響した）

**① 行レベルセキュリティ（RLS）が無い**

PostgreSQL なら「このユーザーはこの組織の行しか見えない」をデータベース自身に
強制させられる。D1 にはこの仕組みが無い。
つまり **アプリ側のコードがうっかり `WHERE organization_id = ...` を書き忘れたら、
他人のデータが見えてしまう。**

これへの対処が、このアプリで一番語れる設計判断になっている（→ 9章）。

**② 1回のクエリでバインドできる変数は100個まで**

CSV で全室を一括登録するときに引っかかった。まとめて INSERT すると上限を超えるため、
分割して実行している。

**③ 途中で判断を挟むトランザクションが使えない**

「A を書いて、結果を見て B をどうするか決める」ができない。
書く内容を先に全部決めてから `db.batch()` でまとめて渡す形に統一している。
**全部成功するか、全部失敗するか**のどちらかになるので、
「契約は作られたのに家賃履歴が無い」という中途半端な状態は起きない。

## 6. Drizzle ORM — SQL を TypeScript で書く道具

### 役割

2つ。

1. **クエリの組み立て** … TypeScript で書いた記述を SQL 文に変換する
2. **マイグレーション管理** … テーブル定義の変更を SQL ファイルとして生成し、順番に適用する

```ts
// こう書くと
db.select().from(units).where(eq(units.organizationId, orgId))

// こういう SQL になる
select * from "units" where "units"."organization_id" = ?
```

### なぜ選んだか

対抗馬は **Prisma**（国内でよく使われている）。見送った理由は、
Prisma が独自のクエリエンジンを必要とし、Workers のような制約のある環境で扱いが重いこと。

Drizzle を選んだ決め手は **SQL に近いこと。**
書いた記述と発行される SQL がほぼ1対1なので、
「なぜ遅いのか」「なぜこの結果なのか」を追える。
ORM が賢く隠してくれるほど、問題が起きたときに手が出せなくなる。

### 弱点（実際にバグを踏んだ）

**生の SQL に落ちた瞬間、型の保護が切れる。**

Drizzle で書きにくい複雑なクエリは `sql` テンプレートで直接書ける。
建物ごとの部屋数を数える箇所でこれを使っていたところ、
Drizzle が列名をテーブル名なしの `"id"` として出力し、
副問い合わせの中で別テーブルの `id` として解決されてしまい、
**常に「0件」を返していた**（コミット `b103fa9`）。

型チェックもビルドも通り、エラーも出ない。画面を見て初めて気づいた。
**「型があるから安全」は、生SQLの内側までは届かない**という具体例。

## 7. Better Auth — 認証

### 役割

ログイン、セッション管理、パスワードのハッシュ化、再発行トークンの発行と検証。

### なぜ選んだか

**自作しないため。**

認証は、素人が書くと確実に事故る領域。
パスワードの保存方法、セッションIDの推測されにくさ、
「そのメールアドレスは存在しません」と返してしまうことによる情報漏れ、
総当たり攻撃への耐性 —— どれも知らないと踏む。

Better Auth は Workers と D1 で動く数少ない選択肢だった。
Auth0 や Clerk のような外部サービスも検討対象だったが、
**家族の情報を外部サービスに預けたくなかった**のと、月額が発生する点で見送った。

### 招待制にした理由

このアプリに一般公開の新規登録は要らない。使うのは家族だけ。
**登録できる入口を塞ぐこと自体が、一番簡単で確実な防御**になる。
アカウントは管理者が発行した招待リンクからしか作れない。

## 8. その他

### Tailwind CSS v4 — スタイル

HTMLのクラス名に直接スタイルを書く方式。`class="text-lg font-bold"` のように書く。

**選んだ理由**：CSSファイルを別に管理しなくて済む。
1人開発だと「このクラス名、まだどこかで使ってるんだっけ」を調べる手間が地味に効いてくるので、
使っている場所とスタイルが同じ行にあるのは楽。

**弱点**：クラス名が長くなり、HTMLが読みづらくなる。好き嫌いが分かれる。

### Vite + @cloudflare/vite-plugin — 開発とビルド

**Vite** が開発サーバーとビルドを担当する。ファイルを保存すると即座に画面に反映される。

**プラグイン**のほうが重要で、これが
**ローカルの開発サーバーを本物の Workers と同じ環境にしてくれる。**
「手元では動いたのに本番で落ちる」を減らすための部品。

### Resend — メール送信

パスワード再発行のメールを送るために使っている。

**なぜ必要だったか**：2章に書いたとおり、Workers は SMTP を使えない。
Cloudflare にもメール機能（Email Routing）はあるが**受信専用**で、送信には使えない。
HTTP の API でメールを送れるサービスが必要で、Resend を選んだ。

### PWA（Web App Manifest + Service Worker）

Android や iPhone のホーム画面に置いて、ブラウザの枠なしで開けるようにする仕組み。

**なぜ**：両親には「アプリ」として使ってほしかった。
アプリストアに出すには審査も年会費も要るが、PWA なら費用ゼロで近い体験になる。

**正確に理解しておくべき点**：置いてある Service Worker は
**「インストール可能」と判定させるために存在しているだけで、何もキャッシュしていない。**
オフラインでは動かない。面接で「オフライン対応しました」と言うと嘘になる。

### Wrangler — Cloudflare を操作するCLI

デプロイ、シークレットの登録、D1へのSQL実行を担当する。
設定は `wrangler.jsonc` に書いてあり、**リポジトリを見れば何がどこにデプロイされるか分かる。**
ダッシュボードで手作業した設定はコードに残らず、後から追えなくなる。

## 9. 技術選定より大事な、3つの設計判断

面接で深掘りされるとしたら、技術の名前ではなくここ。

### ① 空室と現在の家賃を「保存しない」

**問題**：Notion では「空室かどうか」を人が手で切り替えていた。
入居が決まったら空室フラグを消す、退去したら戻す。**忘れると台帳が嘘をつく。**

**判断**：空室状態を持たず、**契約が無い部屋を空室と呼ぶ**ことにした。
家賃も同じで、金額を持たずに家賃改定の履歴を積み、**最新の1件を現在の家賃とする。**

**効果**：手作業の連鎖が消え、更新忘れによる不整合が**起こりようがなくなる。**
「気をつける」で防ぐのではなく、間違えられない形にした。

### ② テナント分離をアプリケーション層で担保する

**問題**：5章のとおり D1 には RLS が無い。
`WHERE organization_id = ...` の書き忘れが、そのまま情報漏洩になる。

**判断**：3段構えにした。

1. すべての業務テーブルに `organization_id` を持たせる
2. **生のクエリを `database/repositories/` の中だけに閉じ込める**。この外に書かない
3. すべてのリポジトリ関数が、第1引数に組織スコープ（`OrgContext`）を取る規約にする

**効果**：書き忘れが起きうる場所が1つのディレクトリに限定される。
レビューすべき範囲が「全コード」から「7ファイル」になった。

### ③ 本番とデモを同じコードで動かす

**問題**：ポートフォリオ用のデモが欲しいが、
コピーして別リポジトリにすると**片方の修正をもう片方に反映する作業が永久に発生する。**

**判断**：リポジトリもブランチも1つのまま、
Cloudflare の環境機能で **同じコードを2か所に配る。**
違いは環境変数 `DEMO_MODE` 1つだけ。デモのデータは毎日 cron で初期化される。

**効果**：反映作業が存在しない。
さらに**デプロイをデモ→本番の順に固定したことで、デモが本番の予行演習になった。**
特にデータベースのスキーマ変更は、これまで家族のデータに一発勝負で当てていた。

## 10. 今なら違う判断をするかもしれない点

正直に書いておく。ここを言えるかどうかで、理解の深さが伝わる。

| 項目 | 現状 | 思うところ |
|---|---|---|
| テストが無い | 手動確認のみ | 導出値のロジック（空室・現在の家賃）は入り組んでいるので、ここだけでも自動テストがほしい。今の最大の弱点 |
| 生SQLの副問い合わせ | 数か所で使用 | 6章のバグを踏んだ。型が効かない領域なので、書くたびに実データで確認する運用が要る |
| Tailwind | 全面採用 | 画面が増えてクラス名が長くなってきた。共通のまとまりを部品として切り出す整理が要る |
| React Router v8 | 採用 | 判断自体は正しいと思う。ただ**求人の数では Next.js に大きく劣る**。技術的な正しさと、転職での有利さは別問題 |

## 用語の対応表

読んでいて引っかかりやすい言葉。

| 言葉 | 意味 |
|---|---|
| エッジ | 利用者に近い場所にあるサーバー拠点。Cloudflare は世界中に持っている |
| SSR | サーバー側で HTML を組み立ててから返すこと。開いた瞬間に中身が見える |
| ハイドレーション | サーバーが返した HTML を、ブラウザ側の React が引き継いで操作可能にすること |
| loader / action | React Router のサーバー処理。読み込みが loader、書き込みが action |
| マイグレーション | データベースの構造変更を、順番に適用できる形で記録したもの |
| バインド変数 | SQL に値を安全に埋め込む仕組み。`?` の部分。SQLインジェクション対策 |
| テナント分離 | 複数の組織のデータが1つのDBに同居するとき、互いに見えないようにすること |
| cron | 決まった時刻に自動実行する仕組み |
| `.server.ts` | サーバー専用のコード。ブラウザに送られないことが保証される |
