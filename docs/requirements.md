# 賃貸物件管理アプリ 要件定義（ドラフト v0.1）

作成日: 2026-08-01

---

## 1. 背景と目的

### 背景

実家で賃貸マンションを所有・管理している。
現在は Notion のデータベースで運用しており、入居・更新・退居・空室の情報は一定の形になっている。

しかし以下の課題がある。

1. **UI が操作者に合っていない** — 主な操作者は50代。Notion はデータベースビューが起点のため、「今何をすべきか」を画面が教えてくれない
2. **手順が運用マニュアル依存** — 別紙のマニュアルを参照しないと正しく操作できない
3. **手作業の連鎖が多い** — 入居確定時に空室を「過去」に、入居完了時に更新レコードを作成、退居時に空室レコードを作成……といった付随作業がすべて人力
4. **ステータスの語彙が分類ごとに異なる** — 同じ「ステータス」列に `進行中/完了/未/準備中/現在/過去` が混在し、意味が文脈依存になっている
5. **修繕が仕組み化できていない** — 設備の型番メモと修理の記録が混在。案件の進行状況が追えず、放置に気づけない

### 目的

- **運用マニュアルの手順をアプリに埋め込み、マニュアルを不要にする**
- 修繕管理を仕組み化し、案件の放置を防ぐ
- （副次目的）GitHub に公開し、ポートフォリオとする

### 成功の定義

- 親が Notion と紙の二重管理をやめられる
- 操作時にマニュアルを参照する必要がない
- 「あの修繕どうなったっけ」が発生しない

## 2. 利用者

| ロール | 想定者 | 権限 |
|---|---|---|
| 管理者 | 本人 | 全操作＋メンバー管理＋設定 |
| 編集者 | 父・母 | 日常の登録・更新操作 |

- 閲覧専用ロールは**設けない**（外部共有の要求は「印刷可能なエクスポート」で満たす）
- 入居者はアプリを使わない
- 管理会社はアプリを使わない

### 利用端末

| 利用者 | 端末 |
|---|---|
| 父・母 | Android（メイン） |
| 本人 | iPhone / PC |

→ **PWA** で対応する。Android Chrome の PWA は Web Push が利用可能なため、通知要件も満たせる。

## 3. スコープ

### やること

- 部屋・駐車場のマスタ管理
- 入居者・契約の管理
- 入居 / 更新 / 退居 のワークフロー（チェックリストと自動遷移）
- 空室状況の管理
- 修繕案件の管理
- 設備台帳と交換目安の可視化
- 印刷を前提とした帳票出力
- CSV インポート / エクスポート
- 契約更新期限の通知

### やらないこと（明示的に除外）

| 除外項目 | 理由 |
|---|---|
| 会計・収支集計 | 集計は不要。入金は「確認済みチェック」のみで足りる |
| 入金消込 | 集金は管理会社が実施。オーナーは送金明細を確認する立場 |
| 法定点検の管理（消防・貯水槽・EV等） | 管理会社に全面委託しているため不要 |
| 入居者向け機能 | 入居者はアプリを使わない |
| 入居者の連絡先・勤務先等の保持 | 個人情報リスク。管理会社が保持しており参照の必要がない |
| 課金・一般公開 | 当面は身内利用。ただしマルチテナント構造は最初から持つ |

## 4. ドメインモデル

### 4.1 Notion 構造からの転換

現在の Notion は「1つのDBに分類（入居/更新/退居/空室）で全部入れる」**イベント台帳型**。
これを **エンティティ + 状態遷移 + 手続き（ワークフロー）** に再構成する。

重要な転換点:

- **「空室」はレコードではなく、部屋の導出された状態**とする（有効な契約が無い＝空室）。空室レコードを手で作る作業が消える
- **入居者を独立したエンティティにする**（現在は氏名・生年を毎レコードにコピーしている）
- **入居/更新/退居は「手続き（Procedure）」**として契約にぶら下げる

### 4.2 エンティティ

```
Organization（組織）
  └ Membership（ユーザー × ロール）
  └ Building（建物）
       └ Unit（貸出単位: 部屋 / 駐車場）
            ├ Lease（契約）
            │    ├ Tenant（入居者）
            │    └ Procedure（手続き: 入居 / 更新 / 退居）
            │         └ ChecklistItem（チェック項目）
            ├ Equipment（設備）
            └ WorkOrder（修繕案件）
                 └ Attachment（写真）
```

#### Unit（貸出単位）

| 項目 | 内容 |
|---|---|
| 種別 | 部屋 / 駐車場 |
| 番号 | `101` `205` / `P1` `P2`（体系が重複しないことを確認済み） |
| 募集家賃 | 空室時の募集金額 |
| 募集開始日 | 空室時のみ |

- 部屋契約と駐車場契約は**別契約**として扱う（実態はセット契約が主だが、モデルを分けたほうが単純）
- 同一の入居者が複数の Unit を借りる場合は Tenant を共有する

#### Tenant（入居者）

| 項目 | 内容 |
|---|---|
| 氏名 | |
| 生年 | |

**これ以上の個人情報は保持しない。**

#### Lease（契約）

| 項目 | 内容 |
|---|---|
| Unit | |
| Tenant | |
| 契約日 | |
| 次回更新予定日 | 契約日の2年後の同日 |
| 状態 | 契約中 / 終了 |

#### RentRevision（家賃改定履歴）

家賃は Lease に直接持たせず、**改定履歴として持つ**。

| 項目 | 内容 |
|---|---|
| Lease | |
| 適用開始日 | |
| 金額 | |
| 事由 | 新規契約 / 更新 / 途中改定 |
| 紐づく手続き | 更新手続きから生成された場合はその Procedure を参照 |

- **現在の家賃 = 本日時点で有効な最新の改定レコード**（導出値）
- 更新手続きの「更新通知内容の決定」ステップで**更新後家賃を確定した時点で改定レコードを予定として作成**し、適用開始日を更新日とする
- 「家賃変更後の金額での入金を確認」がチェックされた時点で確定扱いとする
- 家賃変更なしの場合も、同額の改定レコードを事由「更新」で作成する（更新のたびに1件が残り、履歴が連続する）
- これにより **部屋ごとの家賃推移**が追える。空室時の募集家賃と並べれば、次回募集時の賃料判断の材料になる

### 4.3 手続き（Procedure）とチェックリスト

現行マニュアルの手順をそのままチェック項目として実装する。

#### 入居手続き

- [ ] 契約金お届け明細を受領
- [ ] 委託手数料支払いに関する情報を受領
- [ ] 委託手数料の支払いを確認
- [ ] 契約書をファイリング
- [ ] 家賃送金明細を確認

#### 更新手続き

- [ ] 更新通知内容を決定（決定日を記録／このとき更新後家賃を確定）
- [ ] 更新料金の支払いを確認（年月を記録）
- [ ] 委託手数料の支払いを確認（年月を記録）
- [ ] 家賃変更後の金額での入金を確認（家賃変更なしの場合はその旨を記録）

#### 退居手続き

- [ ] 賃貸借契約解除・金銭明細書を受領
- [ ] 送金明細を確認

> **注**: 現行マニュアルには退居の完了状態が定義されていない（「進行中」のまま終わっている）。本アプリでは送金明細確認をもって完了とする。

### 4.4 自動化ルール（本アプリの中核価値）

現在は人力で行っている連鎖処理を、すべてシステム側で実行する。

| トリガー | 自動実行する処理 |
|---|---|
| 入居手続きの完了 | 契約を「契約中」に。部屋の空室状態を解除。**2年後の更新手続きを自動生成** |
| 更新手続きの完了 | 家賃を更新後の金額に反映。**次回の更新手続きを自動生成**。前回手続きを履歴化 |
| 退居手続きの完了 | 契約を「終了」に。部屋を空室化し、募集開始日・募集家賃の入力を促す |
| 修繕案件の完了 | 対象設備の交換日・型番を更新（任意） |

**操作者がステータスを手で選ぶ操作は発生させない。**

### 4.5 修繕管理

修繕には性質の異なる3つが混在しているため、分離したうえで連携させる。

| 分類 | 内容 | 性質 |
|---|---|---|
| A. 設備台帳 | 型番・設置日・写真 | ストック |
| B. 修繕案件 | 発生から完了までの対応 | フロー |
| C. 交換目安 | 経過年数による棚卸し | A から導出 |

#### WorkOrder（修繕案件）

| 項目 | 内容 |
|---|---|
| 対象 | 部屋 / 駐車場 / 共用部 |
| 対象設備 | 任意（未登録なら案件登録時にその場で作成できる） |
| 発生日 | |
| 内容 | |
| **対応区分** | 自分たち / 業者 / 管理会社 |
| **待ち先** | 今ボールを持っているのは誰か |
| 状態 | 未対応 / 対応中 / 完了 |
| 費用 | 金額のみ（明細は転記しない） |
| 支払済 | チェックボックス |
| 添付 | 写真（請求書の撮影を含む） |
| 最終更新日 | 放置検知に使用 |

##### 設計方針

- **不具合連絡は管理会社経由で入り、その後「自分たちでやる / 業者に投げる / 管理会社に任せる」に分岐する。** この分岐後にボールの所在が不明になることが最大の課題であるため、工程の細分化ではなく「誰がやる」「誰待ち」の2点を明示することを優先する
- **放置の可視化を最重要機能とする。** 14日以上更新のない案件をホーム画面で強調する
- **費用は金額と請求書写真のみ。** 紙の明細を転記する運用は継続しないため、記録項目を最小化する

#### Equipment（設備台帳）

| 項目 | 内容 |
|---|---|
| 設置場所 | 部屋 / 駐車場 / 共用部 |
| 種別 | エアコン、給湯器、コンロ、換気扇 等 |
| メーカー・型番 | 任意（空欄可） |
| 写真 | 銘板の撮影を推奨 |
| 設置・交換日 | |
| 交換目安年数 | |

##### 設計方針

- **初期に全件を登録しない。** 全室 × 設備数 の一括入力は必ず破綻するため、**修繕案件の登録時に未登録の設備をその場で作成できる導線**を用意し、対応したものから台帳が育つ形にする
- **型番の手入力を必須にしない。** 銘板の写真だけで台帳として成立させる
- **交換目安は通知しない。** 耐用年数ベースの自動通知は実際の故障時期とずれるため無視されるようになる。代わりに「設備の経過年数一覧」を提供し、年次の棚卸しや**退去による空室発生時**に確認する運用とする

## 5. 画面構成

### 5.1 ホーム画面（最重要）

Notion の課題は「開くとデータベースが出てくる」こと。本アプリは**タスク駆動**にする。

```
やること (3)
  201号室  更新手続き    更新料の入金確認まち
  305号室  入居手続き    契約書のファイリング
  102号室  給湯器の不具合  業者の見積まち（12日経過）

空室 (2)
  405号室   募集中  78,000円
  P3        募集中

今月の予定
  8/15  203号室  更新予定日
```

- 項目を開くと**次にやることが1つだけ**表示される
- チェックすると自動的に次のステップへ進む
- 放置案件（14日以上未更新）は強調表示

### 5.2 画面一覧

| 画面 | 内容 |
|---|---|
| ホーム | やること / 空室 / 今月の予定 / 放置案件 |
| 部屋・駐車場一覧 | 入居状況の一覧。空室が一目でわかる |
| 部屋詳細 | 現契約・入退去履歴・設備・修繕履歴 |
| 手続き詳細 | チェックリスト。次の1ステップを強調 |
| 修繕一覧 | 未対応 / 対応中 / 完了。放置案件のフィルタ |
| 修繕詳細 | 対応区分・待ち先・写真・費用 |
| 設備一覧 | 経過年数順。交換目安の棚卸し用 |
| 帳票 | 印刷用の各種出力 |
| 設定 | メンバー管理 / インポート / エクスポート |

### 5.3 UI 方針

- 50代の Android 利用を前提とし、**タップ領域を大きく、文字を大きく**
- 一覧より**カード**を優先（表は情報密度が高すぎる）
- 自由入力を減らし、選択と写真撮影で完結させる
- 専門用語よりも現行マニュアルの語彙を優先する

## 6. 帳票・データポータビリティ

### 6.1 位置づけ

紙での保管への要望を、単なる慣習ではなく**「データが消えたらどうするのか」という正当な懸念**として扱う。
この懸念が解消されない限り、親は Notion（またはアプリ）と紙の二重管理を続けることになる。

したがって**印刷は後付けの印刷用CSSではなく、機能として最初から設計する**。

### 6.2 帳票一覧

| 帳票 | 用途 |
|---|---|
| 部屋台帳（1部屋1枚） | 現契約・入居者・入退去履歴・設備・修繕履歴。紙バックアップの主役 |
| 入居状況一覧表 | 全戸の現況を1〜2枚で俯瞰 |
| 更新予定一覧 | 向こう1年分 |
| 修繕履歴 | 期間指定 |

> 実際に親が印刷・保管している書類の内容は未確認。ヒアリング後に見直す。

### 6.3 インポート / エクスポート

- **CSV エクスポート**: 全データ。分かりやすい場所に配置し、「いつでも全部出せる」ことを明示する
- **CSV インポート**: 列マッピングを指定して取り込む。既存 Notion データの移行、および他サービスからの乗り換えに使用

## 7. 公開・ホスティング方針

### 7.1 構成

自前ドメイン配下に、**サブドメイン方式**で配置する。

```
example.com              ポートフォリオのハブページ（作品一覧）
chomen.example.com       管理アプリ（本番）
chomen-demo.example.com  デモ環境
```

#### サブドメインを選択した理由

パス配下（`app.example.com/chomen/`）と比較した結果、サブドメインを採用する。

| 観点 | サブドメイン | パス配下 |
|---|---|---|
| フレームワーク設定 | 不要 | 全アプリに basePath 設定が必要 |
| PWA / Service Worker | スコープが `/` で素直 | スコープが制限され、manifest の設定が必要 |
| **Cookie / localStorage** | **オリジンごとに分離** | **全アプリで共有される** |
| デプロイ | アプリ単位で独立 | ルーティングの一元管理が必要 |

**決定要因は Cookie の分離。** パス配下は同一オリジンとなるため全アプリで Cookie と localStorage を共有する。Cookie の `path` 属性で絞っても同一オリジンからは JavaScript で読めるため、セキュリティ境界として機能しない。

本アプリは実際の賃貸経営データを扱うため、**同一オリジンに置いた習作アプリの XSS が本アプリのセッションに波及するリスクを許容しない**。

「作品を一箇所にまとめて見せたい」という目的は、ハブページからのリンクで達成する。

### 7.2 デモ環境

- **本番とは別オリジン・別データベース**として構築する（同一DB内にデモアカウントを置く方式は採らない）
- トップページの「デモを試す」ボタンからワンクリックでダミー組織にログイン
- 書き込み自由。**日次でリセット**（Cloudflare Cron Triggers）
- ダミーデータは完全な架空。実在しそうな氏名は避ける
- コードは本番と同一。環境変数で切り替える

### 7.3 一般ユーザー登録

**一般公開のサインアップは実装しない。**

登録を開放すると、第三者の賃貸経営データを預かることになり、障害対応・バックアップ・問い合わせの責任が発生する。無償提供であってもこの責任は消えない。

実利用者は3名のため、**管理者が招待リンクを発行する方式**とする。サインアップ画面は不要。

### 7.4 プラットフォーム

**Cloudflare 系**（Workers / Pages）を採用する。

| 理由 | 内容 |
|---|---|
| 商用利用 | 無料プランでも商用利用の制限がない。**Vercel の Hobby プランは個人の非商用利用に限定されており、賃貸経営という収益事業のツールに使うのは規約上問題となりうる**ため候補から除外 |
| コスト | 本番・デモの2環境を持っても無料枠に収まる見込み |
| 運用負担 | VPS 自前運用と比べて保守の手間が小さい。親の日常業務で使うアプリのため、可用性の担保を自分の作業にしたくない |
| 拡張 | アプリを増やす際の追加コストがほぼゼロ |

### 7.5 技術スタック

| レイヤー | 採用 | 理由 |
|---|---|---|
| フレームワーク | **React Router v8**（framework mode） | Workers 上でネイティブに動作し、中間レイヤーが無い。Next.js は Cloudflare では OpenNext を挟む必要があり、バージョンアップ時の破損リスクを避けた |
| スタイル | **Tailwind CSS v4** | 公式テンプレートに同梱 |
| DB | **Cloudflare D1**（SQLite） | Workers ネイティブ。本アプリの規模に対して十分 |
| ORM | **Drizzle** | D1 対応が良好。型安全なマイグレーション |
| ストレージ | **Cloudflare R2**（Phase 2・未導入） | 修繕写真・設備銘板写真。エグレス無料 |
| 認証 | **Better Auth** | Workers / D1 対応。招待制のため実装は軽量 |

> **注意**: D1 には Postgres のような Row Level Security が存在しない。
> マルチテナント分離は**アプリケーション層で担保する**必要がある（データモデル文書を参照）。

## 8. 非機能要件

| 項目 | 要件 |
|---|---|
| 提供形態 | PWA（Android ホーム画面追加を前提） |
| 認証 | メール等によるログイン。**招待制**（一般サインアップなし）。組織単位でデータを分離 |
| マルチテナント | **DB スキーマとアクセス制御は初期から組織単位で設計する**（後付けは困難なため） |
| 通知 | Web Push。対象は**契約更新期限のみ** |
| 個人情報 | 氏名・生年のみ保持。実データはリポジトリに含めない |
| バックアップ | CSV エクスポートで代替 |
| 変更履歴 | 3名で共同編集するため、誰がいつ変更したかを記録（Phase 3） |
| 公開 | GitHub 公開。デモ用シードデータを別途用意し、スクリーンショットもそちらで撮影する |
